# 工作原理

Oh My CPA（OMC）是 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)（CPA）的控制平面。CPA 是网关：保存提供商凭据，并代理客户端的模型请求。OMC 运行在它旁边，不承载普通客户端模型流量（仅内置操练场 Playground 与智能体 Agent 的对话请求会经 OMC 转发），而是通过管理 API 管理 CPA，并记录 CPA 处理过的每个请求。

```text
客户端 ──▶ CLIProxyAPI (:8317) ──▶ 模型提供商
                 ▲   │
        管理 API │   │ 用量记录
                 │   ▼
浏览器 ──▶ Oh My CPA (:8080)
             ├─ 内嵌 Web 控制台
             ├─ SQLite 数据库 (/data)
             └─ 用量采集器
```

## 两个进程

| | CLIProxyAPI | Oh My CPA |
| --- | --- | --- |
| 角色 | 客户端调用的网关 | 面向运维者的控制台与记录 |
| 保存 | 提供商密钥、OAuth 凭据、客户端密钥、`config.yaml` | 请求记录、价格、配额观测、审计日志、偏好 |
| 端口 | `8317` | `8080` |
| 客户端是否依赖 | 是 | 否：OMC 停止时客户端照常工作 |

OMC 要求 CPA v8.0.0 及以上。它按能力探测网关支持的功能，而不是依据版本号猜测；读写范围见 [CPA 集成契约](cpa-v8-compat.md)。

## 两把密钥

- **CPA 管理密钥**：OMC 用它访问 CPA，它同时是控制台登录密码。OMC 不会把它保存在数据库中；唯一的浏览器存储例外是在登录后把密钥镜像写入与 CPAMC 兼容的 `cli-proxy-auth` 条目，供原生插件页面读取，并在退出登录、会话校验失败或下次登录时清除。
- **`OMCPA_MASTER_KEY`**：加密 OMC 数据库中的凭据、载荷与备份。只生成一次且不可更换，丢失后原有数据库记录将无法直接读取，但仍可通过带口令的 `.omcbackup` 备份文件恢复到使用新主密钥的部署中（见[备份与恢复](ops/sqlite-operations.md)）。

## 一个请求的旅程

1. 客户端向 CPA 发送请求，CPA 将其路由到提供商并写入一条用量记录。
2. OMC 的采集器读取这条记录，按价目表计价后保存。
3. 一秒内即可在控制台看到：延迟、Token、缓存命中、费用，以及由哪个密钥、凭据和提供商处理。

配置变更方向相反：在控制台的受检写入路径上，OMC 会先核对上次读取的版本（原生插件页面的直写保留 CPA 的后写覆盖语义），加密备份 CPA 配置，只写入变化的字段，再读回确认；每次变更都会写入审计日志。

## 运行方式

- **每个数据目录只运行一个 OMC。** WAL 模式的 SQLite 需要独占本地磁盘。
- **控制台无特权。** 以非 root 用户、只读文件系统运行。只有可选的 `oh-my-cpa-updater` 容器持有 Docker Socket；升级 OMC 时会校验清单上的项目 Ed25519 签名（升级 CPA 时则按运行容器当前配置的镜像标签拉取）。
- **控制台是单个服务。** Web 界面与 API 共用 `8080` 端口，反向代理只需一个上游。
