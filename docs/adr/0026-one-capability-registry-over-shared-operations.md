# One capability registry over shared operations

Oh My CPA exposes its own management operations to the built-in Agent and to external
agents through one `internal/capability` registry whose entries call the same
`internal/operations` service the console's HTTP handlers call. The Agent runtime and
the `oh-my-cpa mcp` stdio bridge are adapters over that registry: they translate a
transport (model tool calls, MCP tool calls) and never carry a second copy of a
business rule, an allowlist, or a confirmation policy.

The registry is not generated by scanning HTTP routes. Each capability is declared
explicitly with a name, description, JSON Schema, permission (`read`/`write`/
`destructive`), risk, adapter exposure, and handler, and registration fails at startup
on a duplicate name, a missing permission, or a destructive action without a
confirmation preview. Unknown capabilities are refused rather than probed, and neither
adapter may add its own per-feature routing.

External agents authenticate with the CPA management key already configured for the
deployment (`OMCPA_CPA_MANAGEMENT_KEY`), presented as a bearer credential to the
capability endpoints only. There is no second credential store and no per-capability
grant system: the console session and the external agent are two presentations of the
same administrator authority, so adding a token table would add attack surface without
adding a security boundary. The consequence is deliberate and worth stating: the
capability endpoints must still own authorization, approval, and secret handling,
because holding that key is equivalent to holding the console. A browser session is
still required for approval and for private OAuth or secret submission - an external
agent can prepare an operation and read its status, but cannot approve it.
