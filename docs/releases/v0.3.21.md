# Oh My CPA v0.3.21

This release gives the database a copy that leaves the server: an encrypted export, a daily
schedule, cloud destinations and a restore that is validated before it is allowed to land at the
next start. Sign-in is rebuilt as the ordinary form a password manager already knows, with a
month-long option, and the console tells crawlers to stay out. Provider endpoints that live under
an HTTP container name work inside a private network without moving the credential path onto the
public internet. Two smaller changes sit beside them: Claude's own native entry points can be
edited beside the rest of its headers, and a Codex five-hour window with nothing used states its
duration instead of counting down from a minute past five.

## Encrypted database backups

- The System page's storage card carries **Manage backups**, which opens one drawer for the
  schedule, the locations and the two tasks that are not settings — export and restore. The
  request-record meter that sat there is gone; its horizon was never set here, and it is still in
  OMC Settings.
- A backup is a `.omcbackup` file encrypted under an operator passphrase of 12 to 1024
  characters. Inside it is a WAL-consistent `VACUUM INTO` snapshot of the whole OMC database —
  retained usage, locked cost history, audit records and database-backed assets — plus the key
  material needed to read that snapshot on a fresh deployment. A restore therefore needs the
  passphrase, not the CPA management key or the original deployment master key. It does not
  contain CPA's configuration or authentication directory, or the deployment environment.
- The passphrase is set through a guided form with live rules and is required before a schedule
  can be saved or a backup can run. Ordinary responses never return it, and changing it affects
  only files written afterwards, so earlier copies stay readable with the passphrase they were
  written under.
- Validation runs the shipped migrations up to the snapshot's schema version and refuses a
  snapshot newer than the running binary. Retained historical migration records, including
  development-branch ones repaired by earlier forward migrations, do not make an otherwise
  supported backup incompatible.

## Schedule and retention

- The automatic run happens at a wall-clock time of day to the minute (`daily_at_minute`) in the
  server's location, not after an elapsed interval. A run missed during downtime coalesces into
  one overdue run at startup rather than a burst of catch-up copies.
- One backup worker serializes automatic runs, exports and restores. A due run waits for the
  worker; a pending restore blocks backup work until it is applied or cancelled.
- Local retention and each cloud destination's retention are separate settings. Local retention
  applies after a successful local copy, even while a cloud account is unreachable. With
  `keep_local: 0` and at least one cloud destination, the local file is only the upload source:
  it is removed once every destination holds the copy, and the newest local file stays as the
  recovery copy if any destination failed. Pruning at a destination happens only after that
  destination's upload has been read back and its SHA-256 checked.
- Automatic copies live beside the database in `<database-path>.backups`, apart from temporary
  export jobs. Only this schedule's named artifacts count toward its retention.

## Cloud destinations

- OneDrive, Google Drive, S3/R2, WebDAV, SFTP, SMB and FTP are available as peer destinations
  beside the local disk, and cloud-only retention is a valid configuration. A destination only
  ever receives a completed encrypted artifact, never a database handle or an open file.
- The transport is the pinned rclone Go module with only the imported backends, so Docker and
  native installations need no extra service, executable, mount or published port. Its module
  constraints raise the SQLite driver version; migration and repository tests cover that
  integration.
- Google Drive and OneDrive connect through a wizard. The server exchanges the authorization
  code, discovers a default OneDrive, and keeps access and refreshed tokens in the encrypted
  record. A remote server's callback is a loopback address on the browser's computer, so the
  wizard asks for the address from the browser bar and validates its callback address, one-time
  state and PKCE verifier before exchanging the code; it never fetches the pasted URL.
  Authorization sessions expire after fifteen minutes and stay in server memory until the
  connection is saved or cancelled. FTP without TLS exposes transport credentials, and SFTP
  requires an independently verified server public key.
- Connection credentials, the passphrase and refreshed tokens live in a dedicated encrypted
  record that ordinary responses summarize and exported DTOs omit, and that the read-only SQL
  projection cannot query. Blank connection fields keep their saved values. Testing a connection
  is non-mutating and does not prove write permission.

## Restore

- Restore accepts a backup from the local disk, from a cloud destination, or an uploaded file. It
  decrypts and checks the file in a private staging directory, migrates it forward where needed,
  and binds the confirmation to the validated digest. The confirmation applies at the **next
  normal start**; the running database is untouched, and the drawer can cancel the pending
  restore before that.
- Before replacement, startup writes and verifies an encrypted rollback backup of the stopped
  database and preserves its closed main/WAL/SHM files and local key envelope. A restore journal
  lets an interrupted, uncommitted replacement put the previous file set back on the next start.
  The restored database must accept its completion audit before it is committed; if preparation
  fails, startup stops with the current database intact.
- Recovered data is re-wrapped with the target deployment's `OMCPA_MASTER_KEY` and stored
  privately at `<database-path>.key`, so that deployment opens its own local files afterwards.
  Deployment environment — configuration, sign-in key, updater authentication — still comes from
  the target environment.
- A restore rewinds the OMC data timeline: records written after the selected snapshot are absent.
  CPA is not rewound with it, and already-consumed usage records cannot be assumed to be
  replayable. The pre-restore rollback copy keeps the previous history; the restored database
  records the restore event rather than merging audit timelines.
- Restoring turns automatic backups off while keeping the destinations and credentials. A
  restored schedule must not start against the source host's retention namespace, so re-enabling
  it is an explicit step after checking the locations. The confirmation says so.
- Completed restore jobs and their rollback files remain until removed in the drawer. Expired
  exports and unconfirmed uploads are cleaned at startup or when another operation is created.

## Recovery without a console

- The same binary exposes `oh-my-cpa database export|inspect|restore|cancel`, plus `remote-list`
  and `fetch` for cloud artifacts. Inspection needs only the file and its passphrase; local
  export and restore use the target deployment's normal environment. A private passphrase file
  is accepted so the secret does not enter shell history, and the server and the command share an
  exclusive database lock, so stop OMC first.
- A downloaded `.omcrecovery` profile carries the cloud connection settings encrypted under the
  backup passphrase, with no deployment key and no plaintext passphrase. It allows a clean machine
  to list and fetch cloud backups without opening or creating the target database. It is writable
  by design: refreshed tokens are saved back to it. Re-export it after changing credentials or
  reauthorizing an account, and keep independent access to the cloud account — a provider can
  revoke a refresh token.
- A restore into an existing database refuses to proceed if its rollback snapshot cannot be
  created. For a database that cannot be read, preserve the stopped main/WAL/SHM set separately
  first, then restore into a clean database path, which the command can initialize from the
  encrypted backup.

## Sign-in

- The sign-in page is a plain form: one key field, one submit button, and a **Keep me signed in**
  option. On a wide screen a showcase beside it draws clients sending requests into the gateway
  and each one being routed out to a provider. It waits for the session check, is hidden from
  assistive technology, is not mounted on a narrow viewport, and settles under reduced motion.
  Signing in hands the page to the console in one composited view transition; without the browser
  API it simply lands.
- A refused key shakes the field once and puts the caret back in it with the text selected, so
  the next attempt is one paste away. The error itself is unchanged.
- Ticked, **Keep me signed in** issues a 30-day session instead of the 12-hour one. The expiry is
  signed into the HttpOnly cookie, so the browser's own expiry is a convenience rather than the
  check, and rotating the management key still ends every session at once. The console keeps only
  the boolean choice in browser storage; the key itself is never stored.
- The form carries a hidden, read-only account field beside a `current-password` field, which is
  how the browser's password manager and extensions such as Bitwarden and 1Password recognise a
  sign-in form. An offer to save the key is that manager acting with the operator's consent; the
  console never writes the key to page storage or hands it to a credential API.
- Theme preference syncing now mounts behind the sign-in gate. A signed-out theme change is held
  as a local dirty preference and pushed after sign-in, instead of sending a write the server
  refuses.

## Crawlers

- Every response carries `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet, noimageindex`,
  including JSON, assets and the SPA shell, so a console URL that leaked into a crawler's queue is
  still not indexed.
- A disallow-all `robots.txt` is answered at the origin root and, when a base path is configured,
  under that prefix as well — crawlers only read the origin root. `index.html` repeats the
  directive as a meta tag for caches that drop headers. A proxy that forwards only the prefix must
  also route `/robots.txt` to OMC for the advisory file; the header does not depend on it.

## Provider endpoints on a container network

- Model-list pulls and connectivity probes now accept an `http://` provider URL when its hostname
  resolves entirely to loopback or private addresses, which is how a provider reached by a Docker
  service name is addressed. A name that resolves to any public address, or to a mix of public and
  private ones, is refused, as is a failed or empty DNS answer. HTTPS and allowed IP literals
  behave as before.
- Direct connections are pinned to the addresses that were checked, so a later DNS change cannot
  move the credential elsewhere. The configured HTTP `Host` header and the same-origin redirect
  guard are preserved, and a connection that leaves its configured host is refused.
- Each candidate address gets a five-second dial budget inside the caller's own deadline, so one
  stalled address leaves time for the others.
- An HTTP hostname cannot use a proxy: proxy-side DNS would bypass the pinning, and OMC does not
  silently ignore an operator-selected proxy. Add the hostname to `NO_PROXY`, or configure a
  private IP endpoint when the proxy is required. The error says exactly that, and the hint in all
  four console languages states the rule.

## Claude native entry points

- Claude's header configuration now exposes `upstream.claude.header-defaults.native-entrypoints`
  as an editable string list in the visual editor and in configuration search. It can be edited,
  cleared and reverted like any other list, and sibling header settings are preserved.
- Normalization and native-client detection stay CPA's: it trims, lowercases, and drops blanks and
  duplicates in order, and still requires its other strong request signals. An absent or empty
  list adds no custom entry, and OMC keeps no client catalog of its own.
- The write goes through the existing revision-checked configuration path and its encrypted
  pre-write copy.

## Codex five-hour window

- A standard Codex five-hour window that explicitly reports zero usage and a full remaining
  allowance now shows the window duration — `5h` in English, localized elsewhere — instead of a
  countdown that started at `5h 1m` and moved while nothing had been used. The percentage and the
  bar stay visible.
- Positive usage, including an amount small enough to round to 100% remaining, and unknown usage
  keep the live countdown. Other providers, other periods and model-scoped windows are unchanged.
- The reading's details — window label, reset instant, accuracy marker and capacity — moved from a
  native `title` to the shared tooltip, which opens on hover, keyboard focus or a touch tap, and
  closes on Escape or a second tap. This is presentation only; quota data, refresh behavior and
  the shared countdown formatter are untouched.

## System page and dialogs

- The storage card now holds backup status instead of a retention meter, and the retention horizon
  remains a setting in OMC Settings, where it was already changed.
- `AppModal` is one dialog primitive below the pages: a fixed head, a hairline that appears only
  once the body has scrolled, actions in a footer pinned to the bottom edge, and on a phone a
  bottom sheet sized from the visible viewport so a focused form's footer is not left under the
  keyboard. The console's existing dialogs moved onto it, including the vacuum confirmation, the
  icon picker, credential uploads and import, the model picker, request export and the plugin
  store.
- Backups are not offered in the public demonstration. Its database is deleted on every boot, and
  every backup and restore route is refused there.

## Upgrade notes

- Back up `.env` and the data directory or volume before upgrading; follow
  `docs/ops/sqlite-operations.md`.
- Schema version advances to 057 (`057_database_backup_automation.sql`). The migration adds the
  table that holds the encrypted backup-automation envelope and is forward-only; existing data,
  costs, settings and pending inbox payloads are untouched, and an encrypted pre-migration backup
  is taken first.
- No backup runs until a passphrase and schedule are saved. The release adds the capability, not a
  default: an install that upgrades and changes nothing schedules no backup and starts no outbound
  transfer.
- Operators using a backup taken at v0.3.20 or earlier can restore it — validation migrates the
  snapshot forward. A backup from a newer schema is refused with an instruction to upgrade OMC
  first. A restored database still uses the target deployment's environment, including
  `OMCPA_MASTER_KEY` and the CPA management key.
- A confirmed restore replaces the database at the next start, not immediately, and turns
  automatic backups off. Cancelling a pending restore keeps the current data.
- Existing sessions survive the upgrade. The longer lifetime applies to sign-ins that tick
  **Keep me signed in** after upgrading.
- The System page no longer draws a retention meter. The horizon itself is unchanged and is still
  set in OMC Settings → Data retention.
- Provider URLs over `http://` with a hostname now work when the name is private; HTTPS endpoints
  and private IP literals keep their previous behavior. If the deployment sets an HTTP proxy,
  add such a hostname to `NO_PROXY` or switch that endpoint to a private IP.
- No environment variable or Compose change is required. Compose continues to default to
  `latest`. After publication, pin this release with `wiziscool/oh-my-cpa:v0.3.21` or
  `wiziscool/oh-my-cpa:0.3.21`.
